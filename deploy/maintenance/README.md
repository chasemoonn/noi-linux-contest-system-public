# 比赛机有界维护保护

状态：源码默认关闭；趣信奥已于2026-10-27在明确窗口增量启用，进行受控单人试用，未完成生产资格验收。
**不能直接照抄历史维护窗口、boot ID或场次启动。** 当前证据见[发布状态](../../docs/CURRENT_RELEASE.md)。
仅支持独立比赛 VM 的 Ubuntu 22.04、标准 APT/dpkg 路径和原生 TLS/受管桌面入口。
普通 OJ 主机绝不能安装或运行此服务。此目录不包含真实机器标识、审批、凭据或运行日志。

## 原理与边界

`maintenance_guard.py` 在一个主机本地进程中非阻塞取得四个 POSIX 记录锁：
dpkg frontend/backend、APT lists/archives。已存在更新事务时立即完整回退本次获锁，
不等待占住部分锁，不杀事务，不删除或新建包管理锁文件。
持锁之后才进行预检并提供只读 Unix socket；没有网络端口，没有 release/renew RPC。
`systemctl start` 只有在预检完成、socket 就绪且发出 READY 后才算成功。

不停止、禁用或屏蔽原有更新服务/定时器，不写 `/etc/apt`，不使用 `apt-mark hold`。
原本被屏蔽/禁用的策略原样保留，服务退出或主机重启后内核自动释放锁。
这是恢复**执行能力**，不是“积压补丁已经安装”。下一次开机必须先审核并完成必要维护。
预检中的人工确认字段也不是补丁新鲜度自动证明；程序不擅自运行升级或重启。

正常退出会先停止比赛主机的 `nginx.service`，再释放锁，不停止 Docker、不删除任何答案。
控制器/SSH 退出不影响主机保护；主机代理自身异常则由 systemd ExecStopPost 收尾，
watchdog 限制代理卡死。SIGKILL 会先由内核释放锁，不能声称这种极端失败下关闭网关与解锁原子化；
该场应视为失败，控制器停止公开桌面，保留现场，不能自动续租或用重连掩盖。
无法关闭网关时记录失败并恢复更新能力，须人工处置；不能为维持“保护成功”永久阻止安全更新。
其他包管理器、第三方更新器、手工 `systemctl restart`、root 绕锁和云平台操作不受这些锁保护。
负责人须审查这些入口，并继续持有应用共享部署锁/NOI 锁。

## 经新窗口批准后的安装和开赛顺序

以下是需要执行并留证的步骤，不是本仓库自动执行的安装器。不要改变普通 OJ。

1. 独立审查候选代码、systemd 单元及故障测试。先在隔离 Jammy 环境证明真实服务/计时器兼容性，
   包括补执行、手工 APT、controller 崩溃、代理 SIGTERM/SIGKILL/SIGSTOP、重启和异常收尾。
   当前单元测试/CI 不代替这项验收。
2. 在明确维护窗口，确认云实例、SSH 主机密钥、`/etc/machine-id` 和本次 boot ID，
   普通 OJ 健康、无冲突比赛、实际 task 空闲，持双部署锁；启动的只能是该独立比赛机。
   正常完成已有更新、处理待重启、审核安全补丁与更新入口，核对实际 Nginx/Docker/桌面版本。
3. 将本目录 Python 文件按已核对 SHA 安装到 `/opt/noi-maintenance/maintenance_guard.py`，
   单元安装到 `/etc/systemd/system/noi-maintenance-guard.service`。路径链 root 拥有且组/其他人不可写，
   不经符号链接，不全量替换产品。仅 reload systemd 配置，**不要 enable 或设置开机自启**。
4. 在 `/etc/noi-maintenance/lease.json` 写一份 root 私有、单链接普通文件。字段见下表，
   记录真实本次批准而非复制旧时间/boot/tid；最长4小时，启动时至少剩3分钟，容量客户端仍须剩125分钟。
5. 明确启用本次保护服务，确认它发出 READY、四锁有效且主机匹配。正常采集时保留 unit 状态、
   日志、原触发器状态以及包管理/版本证据。启动失败停止排查，不循环尝试直至绿色。
6. 控制器单独启用 `contest_server.maintenance_guard.enabled: true` 并填入固定 `machine_id`，
   保持 native TLS 和受管桌面入口。启用配置不自动安装代理、运行升级或创建许可。
   控制器拒绝自动开机备赛；运行中的保护必须覆盖 OJ 截止 + 至少30分钟归档 +150秒停机余量，
   并早于窗口结束45秒。人工提前截止不缩短既有归档语义。
7. 用全新合成场和原完整校验器开始测试。不得降低逐座质量、连续性、源码/成绩或归档门槛。

| 许可字段 | 要求 |
| --- | --- |
| `schema_version` | 整数1 |
| `dedicated_contest_host` | 明确批准此目标为独立比赛机，布尔true |
| `machine_id` | 此目标的32位小写十六进制主机标识 |
| `boot_id` | 此次 `/proc/sys/kernel/random/boot_id` 原值 |
| `tid` | 全新场次的24位小写十六进制ID |
| `approved_by` | 负责人审计标识，1–64位字母、数字、点、下划线或连字符 |
| `window_start_ms` / `window_end_ms` | 明确批准的 UTC Unix 毫秒，整数；不超过4小时，不自动延长 |
| `maintenance_reviewed_at_ms` | 本窗口内真实完成赛前维护审核的 UTC Unix 毫秒 |
| `maintenance_review_complete` | 人工确认上述审核完成，布尔true；不是可擅自代签的默认值 |

## 收卷、关机和恢复

控制器在实际云 stop 前获取新 nonce 的活进程证明，要求至少150秒余量，保留锁直到关机。
**不要先停止 guard、恢复更新再请求云关机**，否则会产生更新与关机竞态。
正常云关机时，unit 顺序使 Nginx/更新服务先退出，guard 再退出；不会遗留持久 mask 或配置。
仍必须独立确认 STOPPED、取齐归档证据，再精确清理本场合成 OJ 比赛。

若 guard 不可达、证明过期、云 API 超时或包管理正在运行，不得强制中断安装、自动延长窗口，
也不得绕过控制器停机检查。收回桌面入口、保留磁盘和证据，报告无法确认安全关机；
由负责人处理更新事务/新的维护窗口。必要安全收尾不是继续负载的授权。

不计划关机而需提前恢复维护时，须先证明比赛已截止且30分钟归档完成、桌面入口关闭，
再由管理员停止该服务并验证网关关闭、锁已释放、原定时器启用/屏蔽状态未变。
若本来未启用安全更新，不得借此把它打开；若更新任务因锁退出，审核它的下一次调度/补执行。
主机重启后旧许可因 boot ID 不同而不可再次使用；不自动恢复比赛或重新使用旧合成场。

## 不可混淆的验收

新增36项测试会随仓库 Linux CI 执行；Windows 对6项内核锁及3项隔离进程/socket检查明确跳过。
它们只在临时文件上竞争内核锁；真实进程/socket场景使用预检、systemd通知和网关替身，
不接触 CI 主机的 APT，不运行升级，不启动此系统服务。
真实 Jammy/systemd 集成与故障恢复、下一场15+2连续60分钟、实体键盘/本机IME、合作教练签收
仍是独立门槛。默认关闭是避免自动改变已有部署，不是正式办赛可以省略维护保护的意思。
