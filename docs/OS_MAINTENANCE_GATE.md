# 比赛云机系统维护门槛（候选已实现，尚未部署验收）

本页是 2026-10-22 故障后的执行要求。负责人已批准实现和验证有界维护保护；
当前已实现默认关闭的源码候选，不是已经部署的保护功能，也不是新的整场测试窗口。
适用范围仅为独立比赛云机；普通 OJ 主机、学生文件、比赛业务语义不在修改范围内。

## 已发生的故障

15 路真实浏览器正在连续混合负载时，比赛机的系统无人值守更新升级了 Nginx。
10:18:49–10:18:54 的服务停止/启动与全部连接关闭吻合；包管理日志记录了更新命令、
旧/新版本以及二进制升级，服务日志记录了停止/启动，网关日志记录了未关闭连接。
测试按原连续性门槛失败，没有忽略断线、拼接负载或运行到绿色。
完整结果和实际收尾以 [当前发布状态](CURRENT_RELEASE.md) 为准。

共享部署锁和 NOI 锁只能约束遵守它们的应用部署/备赛操作，不能阻止操作系统包管理器重启服务。
因此“普通 OJ 健康、实际 task 队列空闲、17 个容器正常”不是完整的开赛前条件。

Ubuntu 官方说明自动更新由带随机延迟的定时器触发；关机期间错过的任务可能在开机后补执行，
而服务更新可能需要重启。仅看当前没有更新进程，或将下一次计划时间移出比赛，并不能自动证明
整个比赛期间不会触发维护。[官方自动更新说明](https://ubuntu.com/server/docs/how-to/software/automatic-updates/)

本次云机日志显示 Jammy 软件包；不得把其他 Ubuntu 版本的 `needrestart` 默认行为或新的
延后更新选项直接套用成本机原因或修复。直接证据是本机 Nginx 包升级和网关重启。

## 下次开赛前的必要条件

1. 负责人确认维护策略、适用云机、允许的维护时段、恢复责任人和最长延后期限。
   临时延期不能变成永久关闭安全更新；不得为维持一次测量回退已安装的安全补丁。
2. 赛前读取实际发行版、自动更新服务/定时器/其他触发入口、包管理状态及待重启状态。
   区分“未运行”“未启用”“被屏蔽”“等待补执行”；未知或无法证明的状态必须拒绝开赛。
3. 已运行的包管理事务必须正常结束。禁止杀死升级进程、删除锁文件、在安装中间关闭云机，
   或只停定时器就声称已停止正在执行的服务。需要维护却没有足够窗口时，不创建正式场次。
4. 由单独审查、可恢复且有界的方案保证比赛及收卷保护期内不会自动执行会重启关键服务的维护。
   必须保留修改前状态、自动恢复截止、失败恢复和审计记录；单次只读预检不解决检查后的竞态。
5. 检查控制器、网关、桌面和安全更新后的实际版本，并在固定版本上开始全新场次。
   恢复维护触发器时仍需防止更新与关机冲突；不能把剩余未完成事务留给关机中断。

当前实现和受限启用步骤见 [维护保护候选操作说明](../deploy/maintenance/README.md)。
没有改变线上定时器或更新配置。候选须经独立审查和隔离 Jammy 主机的真实 systemd 故障测试，
再在明确维护窗口实施；不能把源码、单元测试或 GitHub CI 当作线上故障已修复。

## 2026-10-22：源码候选

- 主机侧独立 systemd 服务持有四个现有 APT/dpkg POSIX 记录锁；不是 `flock`，
  不删除锁文件，不杀更新，不修改 APT 配置、定时器或原有 enabled/disabled/masked 状态。
- 先取得全部锁，再检查 Jammy、标准 APT 路径、空闲更新服务、干净 dpkg 状态、无待重启及稳定关键服务。
  有更新或未知状态即拒绝，不假设“等几秒就好”。赛前安全更新完成及其他维护入口仍由负责人审核。
- 许可固定到主机、boot ID、新 tid、负责人和不超过4小时的窗口；不提供续租接口。
  同时用绝对时间和含休眠时间的 BOOTTIME 计时，窗口末45秒进入退出保护，不允许借时钟回拨延长。
- 控制器备赛和公开入口检查真实运行进程的 nonce 响应，覆盖比赛截止、完整30分钟归档及150秒关机余量。
  缺失、过期、错主机/场次或时间不足即拒绝；持续对账发现保护失效将比赛置 error 并收回受管桌面入口。
- 正常退出先关闭比赛 Nginx，再释放锁，保留 Docker/学生文件；异常退出有 systemd 收尾和15秒 watchdog。
  没有永久更新配置需要还原。即使关闭网关失败，也不能无限扣留安全更新，必须报警并记为失败。
- 云机停止前保护保持有效，不能先释放锁再调用云 API。失去证明就拒绝停机，避免中断安装。
  启用候选后不自动开机备赛，须由管理员在批准窗口先开机维护和建立保护；不自动重试、续租或开新场。

Windows 上36项新增测试中27项通过，6项真实 Linux 内核锁测试及3项隔离进程/socket测试由 Linux CI 执行；
既有流程64项、配置24项回归通过。Linux 专项覆盖独立进程锁冲突、正在进行事务的无损拒绝、
部分获锁回滚、锁 inode 被替换、链接/缺文件拒绝、进程终止后的释放，以及真实本地socket断连、
SIGTERM/到期退出和SIGKILL后的独立收尾入口；主机维护命令和网关使用隔离替身，这些不是实际无人值守升级或
真实 systemd watchdog/重启验收。GitHub CI 的实际结果以对应提交运行记录为准，不预填通过。

技术依据：[APT 锁实现](https://github.com/Debian/apt/blob/main/apt-pkg/contrib/fileutl.cc)、
[Linux 记录锁语义](https://man7.org/linux/man-pages/man2/fcntl_locking.2.html)、
[systemd 服务监督](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)。
这套保护仅覆盖遵守标准锁的 APT/dpkg 更新；不能阻止 root 故意绕锁、直接重启服务或云平台重启。
因此它不是安全隔离边界，更不是可跳过部署锁、独立审查和下一场完整容量验收的理由。

## 保护方案本身的验收

- 有更新事务正在进行、开机补执行、手动启动更新、两个管理者并发进入时，均不能误判可开赛。
- 控制器异常退出、连接断开、窗口到期和主机重启时，延后措施不永久残留，恢复有可验证记录。
- 恢复时保留原有启用/禁用状态，不意外开启原本禁用的服务，不恢复不存在的配置，不泄露日志凭据。
- 自动更新造成的服务中断与普通网络抖动分别记录；不能通过放宽 WebSocket 连续性门槛消除失败。
- 修复后仍需新的 15+2、连续 60 分钟、150+150 编译、60 网页、逐座质量及完整 30 分钟归档关机测试。
  既有失败场次保留，实体键盘/本机 IME、合作教练独立办赛和负责人服务责任签收仍单独验收。
