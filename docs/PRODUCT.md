# NOI Linux 全真模拟赛系统：产品说明

> 当前阶段：**Alpha**<br>
> 已验证：官方 NOI Linux 桌面的单座完整闭环<br>
> 尚未认证：官方 GNOME 镜像的 15 个正式座位 + 2 个备用座位、连续 60 分钟容量验收

## 项目定位

本项目是一套面向学校、培训机构和小型竞赛组织者的社区开源参考实现。它在已有 Hydro OJ 之外，为每名选手提供相互隔离的 NOI Linux 图形桌面，并编排赛前材料、座位预热、选手发放、网页或文件夹递交、严格截止、收卷回传和比赛云主机生命周期。

它解决的是“如何安全、可重复地组织一场接近线下复赛环境的临时模拟赛”，而不是重新实现一个在线评测系统。Hydro 仍然负责账号、比赛、题目、评测记录和教师侧成绩观察；本项目负责远程桌面与比赛过程控制。

首个维护者支持的部署组合见 [支持矩阵](SUPPORT_MATRIX.md)。开源化、独立复现和容量签字计划见 [开源路线图](OPEN_SOURCE_ROADMAP.md)。

## 独立项目声明

本项目是独立的社区项目：

- 不是中国计算机学会（CCF）或 NOI 的官方软件；
- 不是 Hydro 项目官方组件，也不代表 Hydro 官方提供部署或运维支持；
- “全真模拟”描述的是产品目标和环境还原方向，不表示获得 CCF、NOI 或任何省级竞赛组织方认证；
- 使用者必须根据本地比赛规则、网络条件和风险要求完成自己的赛前验收。

项目中出现的 CCF、NOI、NOI Linux、Hydro 等名称仅用于说明兼容对象和使用场景。

## 适用对象

### 教师与比赛组织者

- 已经在 Hydro 中维护账号、题目和 OI 赛制比赛；
- 希望学生在统一的 NOI Linux 图形环境中编写、编译和自测；
- 需要网页递交、文件夹到点回收或双轨备份；
- 愿意在正式比赛前完成真实账号、真实链路和完整截止收卷演练。

### 系统维护者

- 能维护 Linux、Docker、Caddy、PM2/Nix 和云主机；
- 能隔离运行时密钥、验证镜像摘要并保留审计证据；
- 能理解临时公网直连的明文风险，并根据现场网络决定是否启用；
- 能在任何异常下优先保护原有 OJ，而不是为了恢复桌面盲目重启整套服务。

## 不属于本项目的范围

- 不替代 Hydro 的题库、比赛、判题机或权限系统；
- 不承诺未经本地验收的正式竞赛、超出支持矩阵的云厂商或任意人数规模；
- 不把旧 XFCE 镜像的历史容量数据当作官方 GNOME 镜像的容量结论；
- 不支持用宿主机多 Linux 账号替代“一名选手一个容器”的正式隔离模式；
- 不把裸 HTTP 直连描述为长期公网安全方案；长期目标是在比赛机本地终止 HTTPS；
- 不允许 AI 接触正式隐藏测试数据、运行时密钥或未经清理的生产配置。

## 一场比赛的标准生命周期

1. 教师在 Hydro 创建 OI 赛制比赛，确认题目、开始时间、截止时间和报名名单。
2. 编排器登记比赛并冻结 Hydro 时间、赛制、题目映射和材料 revision。
3. 教师审核题面、自测数据、文件读写名称和生成报告，然后明确批准。
4. 系统按“正式人数 + 备用位”提前启动并逐个验收隔离桌面；报名只绑定已经验收的座位。
5. 到发放时间后，系统通过 Hydro 站内消息提供座位入口、准考证号和密码。
6. 学生在 NOI Linux 中完成编写和自测，并按本场模式使用网页、答案文件夹或两者递交。
7. 截止时比赛机本地计时器先冻结全部座位，再关闭桌面入口；控制面随后收卷、静态检查并幂等回传 Hydro。
8. 报告和回传证据完整后，系统撤销学生网络入口并停止比赛云主机；普通 OJ 继续提供服务。

## 七条比赛契约

以下契约是产品边界，不是“尽量做到”的功能列表。任何部署如果不能证明这些契约，就不能被称为本项目的受支持比赛运行。

### 1. 普通 OJ 连续性契约

比赛桌面、编排器或比赛云主机的故障不得扩大为普通 Hydro OJ 故障。赛前、赛中和赛后都必须能够分别证明 OJ 首页、登录和评测链路正常。桌面恢复应优先处理单座位或比赛专用组件；不得把重启 Hydro、Caddy 或整台 OJ 主机当作常规恢复手段。

### 2. 比赛事实冻结与教师批准契约

Hydro 的开始时间、截止时间、赛制和题目映射必须在备赛前冻结并再次核对。题面、PDF、自测数据、manifest 和 validation report 必须属于一个不可变 revision，教师批准前不能发放。AI 只能起草清理后的题面和自测材料；正式隐藏数据内容、密钥和生产配置不得发送给 AI。

### 3. 官方桌面身份契约

正式座位必须来自基于官方 NOI Linux 介质构建的桌面镜像，并解析到不可变 image ID。镜像必须携带编排器要求的 `org.noi.desktop.contract=finalizer-status-v1` 标签；缺失、摘要漂移或契约版本不符时，在创建、扩容或替换座位前失败关闭。旧 XFCE 镜像只可作为明确标记的应急回退，不能冒充官方 GNOME 容量证据。

### 4. 一人一座与答案持久化契约

每名选手使用独立容器、独立凭据和独立答案挂载。座位网络必须是 Docker internal 网络并关闭容器间通信，且设置 CPU、内存、PID 和共享内存边界。容器重启、单座故障替换或控制面短时失联不得丢失已经可靠写入的答案；故障处理不得改变其他学生的 `uid → slot` 绑定。

### 5. 递交可靠性与 OI 盲测契约

网页递交必须先可靠写入持久队列，再幂等创建 Hydro RID；相同请求重试不得产生重复记录。文件夹模式必须从截止后冻结的目录收卷；双轨模式必须按公开、确定的优先级选择最终版本。违反文件 I/O 规则时要保留原代码并形成可审计的强制零分提交。比赛期间普通学生不能看到分数、测试点、评测结果或排行榜，教师可以按权限实时观察。

### 6. 严格截止与证据保全契约

精确截止不能只依赖 OJ 或编排器轮询。比赛 ECS 上的持久化 systemd timer 必须在冻结的截止时刻先暂停全部座位，再停止本机桌面入口；即使控制面失联，也不再接受新的桌面操作或文件写入。收卷只能读取冻结后的证据，失败时保留原目录、报告和队列状态，并允许安全重试，不能用“重新备赛”覆盖本轮记录。

### 7. 限时开放与失败关闭契约

学生入口只在唯一有效且未截止的 `ready` 比赛中开放。直连模式必须使用比赛机专属安全组和固定 EIP，关闭态与开放态都满足精确白名单；发生拓扑漂移、规则冲突、过期比赛、收卷、手动关机或无法确认撤销时，系统必须撤销受管规则，必要时停止比赛云主机兜底。赛后应同时证明入口关闭、受管规则清零、待处理队列清空和云主机进入停止计费状态。

## 支持的递交方式

| 模式 | 适用场景 | 最终版本规则 |
| --- | --- | --- |
| `web` | 模拟网页程序回收 | 每次明确提交立即持久化并送入 Hydro；每题最后一次有效提交为准 |
| `folder` | 模拟 NOI/CSP 答案目录回收 | 截止冻结后从 `准考证号/题目名/题目名.cpp` 收卷并送评 |
| `both` | 推荐的日常模拟赛模式 | 网页递交为正式版本；没有网页版本时使用截止时的文件夹备份 |

无论选择哪种模式，教师都必须在赛前用普通学生账号验证 OI 盲测，并在赛后核对收卷报告与真实 Hydro RID。

## 当前成熟度

截至 2026-08-09：

- 官方 NOI Linux 桌面的单座登录、noVNC、编译、保存、网页/文件夹递交、Hydro 回传、截止收卷、撤销入口和停机闭环已经通过维护者环境验收；
- 裸 HTTP 固定 EIP 直连是为短时模拟赛优化交互体验的 **Alpha 路径**，已完成单座路径验证，但存在公网明文、浏览器提示和部分校园网络不兼容等限制；
- 官方 GNOME 镜像的 15 个正式座位 + 2 个备用座位，连续 60 分钟真实操作容量验收尚未完成最终签字；
- 历史 40 座测试使用旧 XFCE 备用镜像，只能作为链路和旧镜像证据，不能外推为当前容量承诺；
- 在完成 [路线图](OPEN_SOURCE_ROADMAP.md) 的容量门槛前，本项目不得宣传为“15 人已认证”或“正式比赛开箱即用”。
