# 开源路线图与验收门槛

本路线图把“代码可以查看”推进为“边界清楚、能够独立复现、证据可审计的开源产品”。它不以功能数量作为完成标准，而以 [七条比赛契约](PRODUCT.md#七条比赛契约) 是否在明确的 [支持 profile](SUPPORT_MATRIX.md#首个维护者支持-profile) 中得到证明作为放行条件。

## 当前结论

截至 2026-08-09：

- 维护者环境中的官方 NOI Linux 单座完整闭环已经通过；
- `aliyun-hydro5-pm2-direct-v1` 的裸 HTTP EIP 数据面处于 Alpha；
- 官方 GNOME 镜像的 15 个正式座位 + 2 个备用座位、连续 60 分钟容量签字尚未完成；
- 在第四阶段门槛全部通过前，不得发布“15 人已认证”“正式比赛开箱即用”或等价宣传。

各阶段可以并行准备材料，但不能跳过前一阶段的放行门槛来扩大支持承诺。

## 阶段一：开源产品基线

### 目标

让第一次访问仓库的人能够准确理解产品、风险、成熟度和维护范围，不需要从交接记录或部署脚本反推结论。

### 交付物

- 产品定位、独立项目声明、适用与不适用场景；
- 七条比赛契约和标准比赛生命周期；
- `aliyun-hydro5-pm2-direct-v1` 支持矩阵；
- 当前单座证据与 15+2 未签字状态的醒目标注；
- 明确的开源许可证、贡献指南、安全报告方式和行为准则；
- 学生、教师、维护者三类入口文档；
- 使用固定脱敏 fixture 生成的架构图与界面截图，不包含生产地址、token、账号或答案。

### 放行门槛

- [x] 项目不再暗示由 CCF、NOI 或 Hydro 官方开发、认证或支持；
- [x] 所有容量与安全声明都带有适用 profile、日期和证据边界；
- [x] 仓库包含维护者明确选择的许可证；
- [x] 文档中的命令、路径、版本和链接纳入公开发布检查；
- [x] 公共文档和演示资产通过密钥、token、个人信息、真实答案和公网地址检查；
- [ ] CI 继续通过，文档改造不改变运行时行为。
- [ ] 按 [首次公开发布检查单](PUBLICATION_CHECKLIST.md) 从审过的 commit 建立不包含现场旧历史的公共仓库。

### 当前状态

接近完成。产品入口、许可证、贡献与安全治理、支持边界、脱敏演示资产和公开发布检查已经落地；待本批改动通过完整 CI 并发布后，阶段一才正式关闭。

## 阶段二：可重复构建与参考部署

### 目标

让没有参与历史开发的维护者能够在全新、隔离的基础设施上，从固定输入得到同一类不可变产物，并能安全回滚，不依赖聊天记录、个人目录或线上热修。

### 交付物

- 官方 NOI Linux 介质来源、SHA256、根文件系统提取过程和 attestation；
- 锁定的依赖版本、桌面镜像契约和不可变镜像 digest；
- `aliyun-hydro5-pm2-direct-v1` 的无密钥示例配置与逐项 profile 校验；
- 编排镜像、Hydro 插件和部署脚本的版本关联；
- release manifest、SHA256SUMS、SBOM、兼容矩阵、升级和回滚说明；
- 新主机安装、卸载和失败关闭演练；
- 严格受限的 AI 本地复现指令：默认不联网写生产、不接触密钥和隐藏数据，每阶段都有停止点。

### 放行门槛

- [ ] 全新 OJ 测试主机和全新比赛 ECS 仅依赖已发布文档与产物即可完成部署；
- [ ] 构建两次得到相同的关键输入摘要、桌面契约和可解释的产物差异；
- [ ] 所有容器使用精确 digest，运行时 `.env`、`config.yaml`、状态库、收卷数据和密钥不进入镜像或 Release；
- [ ] 安装前后普通 Hydro OJ 的首页、登录和评测基线一致；
- [ ] 回滚能恢复上一版插件、编排器和 Caddy 配置，且不删除比赛证据或用户数据；
- [ ] CI 覆盖 Python、Node、部署脚本、文档链接以及配置/密钥泄漏检查；
- [ ] 任一关键校验失败时停止在关闭状态，而不是自动降级到未验证模式。

### 当前状态

部分具备。仓库已有 CI、镜像契约、官方介质校验、安装脚本和只读健康检查；统一 release manifest、SBOM、独立重建记录和公开回滚演练仍待补齐。

## 阶段三：单座参考 profile 独立验收

### 目标

在全新 `aliyun-hydro5-pm2-direct-v1` 环境中，由至少一名未参与实现的复核者完成一名普通学生和一名教师的真实闭环，证明七条比赛契约不是维护者机器上的偶然结果。

### 必测流程

1. 用真实普通学生账号和教师账号创建短时 OI 比赛，不复用正式学生数据；
2. 核对官方镜像 digest、桌面契约、材料 revision、题目映射和截止 timer；
3. 验证 T-5 前不泄露凭据，T-5 后站内消息、HTTPS 控制页、direct Alpha 入口和 HTTPS 兼容入口行为正确；
4. 在桌面完成中文输入、编译、自测、保存和容器重启后的答案持久化；
5. 验证逐题网页优先与目录兜底，包括重复递交、网页版本不被目录覆盖、目录截止提交、源码下载 SHA256 和不合规文件 I/O 强制零分；
6. 教师能实时观察，普通学生在比赛中看不到结果、分数和排行榜；
7. 注入一次可恢复的送评或网络故障，证明幂等重试不重复创建 RID，证据不丢失；
8. 实际等到截止 timer 触发，证明先暂停座位、再关闭 nginx，截止后新提交被拒绝；
9. 收卷完成后核对报告、Hydro RID、队列清零、入口关闭、安全组收敛和 ECS 停止计费；
10. 全程持续探测普通 OJ，确认比赛故障与恢复没有造成 OJ 中断或非常规重启。

### 放行门槛

- [ ] 七条比赛契约各有时间戳、命令输出或报告文件作为证据；
- [ ] 正式目录、逐次递交和截止快照的最终 SHA256 与预期一致；
- [ ] direct HTTP 的明文风险、浏览器提示和校园网络兼容限制由复核者明确签收；
- [ ] 未知 token、未发放座位、非 `ready` 比赛和截止后入口均失败关闭；
- [ ] 最终没有活动座位、受管学生规则或待处理送评/通知队列；
- [ ] ECS 为停止计费状态，普通 OJ 健康；
- [ ] 另一名维护者对脱敏证据完成复核并签字。

### 当前状态

维护者环境的单座闭环已通过；独立第三方按公开文档从零复现和签字仍是正式开源 Release 的门槛。

## 阶段四：15+2 容量资格与稳定发布

### 目标

在同一个不可变官方 GNOME 镜像 digest 上，完成 15 个正式座位和 2 个备用座位的连续 60 分钟真实操作与故障演练，形成首个可公开引用的容量签字。

### 测试条件

- 使用 `aliyun-hydro5-pm2-direct-v1` 的 16C64G 阿里云专用 ECS、固定 EIP 和专属安全组；
- 17 个座位全部来自同一官方镜像 digest 和同一已批准材料 revision；
- 15 个正式座位使用真实浏览器会话，保持 `quality=9`、`compression=2`，持续进行编辑、编译、PDF 阅读、自测和递交；
- 2 个备用座位完成预热和验收，其中至少一个实际执行故障接管；
- 使用真实目标地域、校园或等价出口，记录 direct 与兼容入口差异；
- 维护者和独立复核者共同观察并保留脱敏原始指标。

### 60 分钟必测项目

- 全部座位的 GNOME、noVNC、PDF、自测数据、答案目录和网页入口完整率为 100%；
- 编程字符、中文输入切换、长源码、UTF-8/LF 规范化、上传下载 SHA256 和编译全部通过；
- 15 个座位持续交互并多轮同时编译，单个学生死循环不能使其他座位失去交互；
- 注入一个普通座位容器重启，答案保持；再注入一个座位故障并切换到备用位，其他 `uid → slot` 不变；
- 记录宿主 CPU/内存、每容器 CPU/内存/OOM、出口 Mbps、RTT、丢包、WebSocket 重连次数和键到画面的 p50/p95；
- 同时验证教师实时观察与普通学生 OI 盲测；
- 截止时 15 个正式座位全部由本地 timer 冻结，入口关闭，截止后没有新证据混入；
- 15 名学生的收卷、静态检查、最终来源选择、RID 和报告全部完成且可核对；
- 赛后受管规则、活动座位和待处理队列为零，ECS 停止计费，普通 OJ 全程健康。

### 容量签字门槛

- [ ] 连续 60 分钟内没有无法恢复的座位故障、答案丢失或全场服务中断；
- [ ] 15/15 正式座位完成规定操作和最终收卷，2/2 备用位完成验收，至少 1 次备用接管成功；
- [ ] 资源、网络和交互 p95 指标有原始数据、阈值解释和容量余量判断，不能只写“感觉流畅”；
- [ ] 没有跨座访问、普通互联网绕过、凭据提前泄露或 OI 结果泄露；
- [ ] 截止、收卷、撤销规则和停机全部满足七条比赛契约；
- [ ] 维护者与独立复核者共同签署带日期、commit、镜像 digest、实例规格和材料 revision 的报告；
- [ ] 已知限制、故障恢复和回滚步骤同步到支持矩阵与 Release Notes。

只有全部门槛通过，`aliyun-hydro5-pm2-direct-v1` 才能标记为“15+2 容量已签字”。任何镜像、实例规格、桌面数据路径或关键资源限制变化都会使容量证据失效，并要求重新验收。

## 发布分级

| 分级 | 最低条件 | 允许的公开表述 |
| --- | --- | --- |
| Alpha | 阶段一基线 + 维护者单座闭环 | 单座主路径已验证，存在明确限制，不承诺 15 人容量 |
| Beta | 阶段二完成 + 阶段三独立复现签字 | 首个 profile 可独立复现，正式使用前仍需本地演练 |
| 15+2 Capacity Qualified | 阶段四全部签字 | 仅对报告中的精确 profile、digest、规格和网络条件声明 15+2 容量 |
| 1.0 稳定发布 | Beta、容量签字、治理/安全/回滚文档和至少一次发布演练全部完成 | 在支持矩阵内提供稳定维护承诺，仍不代表 CCF、NOI 或 Hydro 官方认证 |

## 证据与声明规则

- 每项验收必须记录日期、Git commit、镜像 digest、profile、实例规格、材料 revision 和参与人数；
- 旧镜像、旧链路、不同云规格或不同人数的证据不得跨边界复用；
- 截图和日志进入公共仓库前必须删除 token、密码、账号、IP、AccessKey、私钥、比赛 ID 和答案内容；
- 失败记录与修复记录同样属于验收证据，不得只保留最终成功截图；
- 文档中的“支持”“验证”“目标”“实验性”必须使用 [支持矩阵](SUPPORT_MATRIX.md#状态术语) 的定义；
- 一旦发现实际状态低于公开声明，应先下调支持矩阵和 Release 说明，再继续修复。
